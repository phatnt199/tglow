v0.11.0 — Ctrl-J, and binaries built where they run

`<C-j>` breaks a line while you are writing, alongside `<A-Enter>`. Enter still
sends; the two can never be confused, because Enter arrives as `0x0D` and
Ctrl-J as `0x0A`.

It is bound twice on purpose. A terminal speaking the kitty keyboard protocol
reports Ctrl-J as `<C-j>`; one that is not sends the bare byte `0x0A`, which
comes through under a different name entirely. Binding only the first would
have worked on some terminals and done nothing at all on xterm or Alacritty,
so both are bound and both are tested.

## Where the binaries come from

Until now all four were cross-compiled on one Linux machine. That worked, but
it could only ever be checked as far as the file format — the v0.10.0 notes had
to say plainly that the macOS and Windows binaries had never been run.

Three of the four are now built by GitHub Actions on a runner of their own
operating system — Linux, Apple silicon and Windows — by a Bun that resolved
that platform's own native renderer, and each of those is started there before
it is published. The whole test suite has to pass before any of them is built.

The fourth, macOS Intel, still cannot be: GitHub no longer offers an Intel
macOS runner. It is cross-compiled from Apple silicon with the real
`darwin-x64` renderer, and nothing runs it.

Be clear about what the rest buys you: it proves the binary starts, its bundled
JavaScript executes, and it reaches the configuration layer. It does not draw
to a terminal — that needs a pty and a logged-in account, neither of which
belongs in CI. A build that cannot render would still get this far. So the
request stands: if a macOS or Windows build misbehaves once it is on screen,
[say so](https://github.com/phatnt199/tglow/issues).

Nothing about installing changes. Four files and one `tglow.sha256` covering
all of them, exactly as before.
